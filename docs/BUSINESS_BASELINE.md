# 业务基线

> 规则版本：reimbursement-v1-002。本文描述当前产品规则；外部企业数据由本地 Stub 提供。

## 1. 核心对象

| 对象 | 业务含义 |
| --- | --- |
| 报销单 Claim | 一次申报的入口、主体、公司、账户、独立总额、关联与状态 |
| 明细 ClaimLine | 一笔用途明确的费用，有金额/日期/项目或类型及材料归属 |
| 材料 Material | 稳定原件身份、内容摘要、受控页、当前识别事实与版本 |
| 材料事实 | 模型从原件提取的角色、金额含义、日期、票号、购销方与付款/退款状态 |
| 人工决定 | 允许范围的付款金额、疑似重复确认及处理原因 |
| 字段建议 | 对已归行事实的候选值、原值、来源、保护状态与采纳批次 |
| 审核报告 | 对确定版本的检查、证据、下一步及是否满足提交条件 |
| 提交记录 | 版本冻结、快照、幂等命令、排期和模拟 OA 结果 |
| 关联审批 | 实例 ID、业务单号、类型、归属、状态和日期范围 |

## 2. 角色和材料计入

| 角色 | 可计入金额 | 主要限制 |
| --- | --- | --- |
| payment | 已完成支付的有效实付，必要时扣减关联且已完成退款 | 原价、优惠、余额、待付款、申请退款不能直接当实付 |
| tax_invoice | 有效税务发票价税合计 | 逐张核对购买方；手工付款金额不能替代税票认证 |
| title_exempt_transport_receipt | 有效铁路等免抬头交通票据金额 | 保留实际乘车/行程日期，不当普通公司税票处理 |
| supporting_document | 不补付款或税票金额 | 行程与事实佐证仍可参与审核 |
| unknown | 不自动计入 | 保留候选，符合付款人工确认边界才可确认 |

上传区域和文件名不决定最终业务角色。金额相同也不代表两张材料属于同一费用，材料归属由员工确认。

## 3. 独立申报与金额关系

系统保留三个不同概念：**员工独立申报总额**、**费用明细金额**、**材料有效支持金额**。它们不是同一个自动计算字段。

1. 总金额在基本信息由员工填写，初始为空；识别、建议、导入、重新分配不会生成或覆盖总额。
2. 每行可手填金额或确认材料建议；人工/导入金额不会被后台识别静默覆盖。
3. 总额必须为正数，且与明细和相差不超过 **0.01 元**。
4. 普通入口每行申报不能超过有效付款；付款高于申报允许少报并提示。
5. 需票行申报不能超过有效税票/免抬头交通票金额；佐证和 unknown 不补足税票。
6. 供应链专属入口免付款，但每行必须有税票，申报额与有效票额按 0.01 元匹配。
7. 最终提交重新运行当前版本规则，不能只依赖前端状态或模型结论。

例：付款与发票均识别 88 元、明细为 88 元，员工申报总额为 100 元时，整单金额检查失败；员工核实并改为 88 元后，旧报告失效，必须重新审核。识别出错时，不能把同一识别值同时当作员工的独立声明。

## 4. 二十组规则

| 规则 | 业务要求 |
| --- | --- |
| R-01 | 材料须有可用事实、正确归属与执行模式；失败、未准备或 provider/fixture 混用不能冒充完成 |
| R-02 | 多金额中区分原价、优惠、实付、余额和订单金额，不能取最大值或凑申报额 |
| R-03 | 已完成且能关联原支付的退款才扣减；申请中/关系不明保留待核对 |
| R-04 | 多笔独立交易按可靠 ID 处理，同一交易重复展示不能重复相加 |
| R-05 | 原件重复和明确同票排除；疑似重复需确认，不凭“不同”覆盖明确重复 |
| R-06 | 识别金额、候选、可计入金额、付款人工确认和员工申报分开 |
| R-07 | 普通行需有效付款支持；超报阻止，少报提示 |
| R-08 | 需票行需有效税票/交通票支持；佐证不代替发票 |
| R-09 | 人工独立正数总额与明细和匹配；供应链另按专属税票关系核对 |
| R-10 | 金额字符串/Decimal 精确核算，容差统一 0.01 元 |
| R-11 | 有票/无票入口分流；无票不混入发票；专属免付款不向普通身份开放 |
| R-12 | 实际用途、项目、费用结构及必要字段由员工确认，不由模型编造 |
| R-13 | 付款公司及合法账户明确；社保仅默认建议，选择不同主体不因此强拦 |
| R-14 | 税票购买方与所选付款公司逐张核对；不能用总额足够掩盖错抬头 |
| R-15 | 免抬头交通票与普通税票分流；缺抬头并非所有材料都按同一方式处理 |
| R-16 | 日常团建、差旅和打车按适用规则要求业务审批；项目制不按关键词新增要求 |
| R-17 | 审批查询按报销归属人；业务单号先解析为实例 ID，不混用主体或借用同行审批 |
| R-18 | 差旅逐行关联审批，范围首尾包含；开票日不单独作为实际行程冲突 |
| R-19 | 实际日期冲突需独立人工说明；可靠实际日期未知时明确提示，不伪装已核实 |
| R-20 | 权限、版本、必要检查及提交状态由程序控制；管理员和模型都不能通用绕过 |

规则在`backend/src/reimbursement/rules.py`执行；识别事实、材料去重和提交事务另由相应服务落实，不把规则编号等同于一段同名 if。

## 5. 自动获取审批

进入草稿和变更归属人后，系统调用归属人的审批查询接口，展示类型、标题、日期范围、状态和业务单号。员工点击卡片关联，可多选；读取失败可刷新，未找到可展开单号查找。

该过程不自动选择所有审批，也不把出差列表第一条套入每行。差旅明细仍需确定具体出差实例。项目制和普通日常的关联要求分别处理。当前查询对象为合成目录，实际 OA 读取可接入相同业务接口。

## 6. 差旅日期

费用日期、票据实际日期与普通开票日期分别表达。差旅每行比较对应审批的日期范围，起止日包含在范围内。普通税票开票晚于出差不单独判冲突。

可靠的实际日期冲突时，员工提供4—500字符的真实说明；不能用系统摘要代替。没有可靠实际日期时按规则允许 unknown 并提示。多条审批不得用首条兜底。有效审批状态缺字段、跨路径复用、借同行和替票豁免没有通用自动决定。

## 7. 提交与排期

提交必须由用户最终确认。服务端检查身份、当前修订、报告来源/签名、材料与金额，再保存不可变快照和持久提交任务。同一报销即使换幂等键也只对应一个提交记录。

启用月度排期后，上海时区1—20日进入当月21日09:00池，21—25日走即时路径，26日至月底进入下月21日池。池任务遵守09:00—18:00、FIFO与持久三分钟节流。默认本地体验关闭排期。

发送结果 unknown 时先查询，不盲目重建；台账旁路失败单独恢复，不重建模拟 OA。允许状态可撤销并复制草稿；旧快照和成功实例不被修改。历史自动总额的副本需要重新填写人工总额。

## 8. 台账与反馈

台账以模拟 OA 创建事件形成候选，包含序号、票号、销方税号/名称、购方税号/名称、开票日、项目、金额、税额、价税合计、入账时间、是否入账共13列。默认 audit 不写投影；显式 sync 只写本地模拟表。只有系统写入、当前内容未改且未入账的行可自动回滚，冲突保留。

反馈按批次/收件人去重，随机 token 仅摘要入库，专属链接只授权本邀请；同邀请答卷唯一。明确失败重试轮换 token，旧链接失效。两项必选、一项最多500字符建议；CSV 导出避免公式注入。模拟邀请不发送真实员工通知。

## 9. 不自动决定的边界

审批状态缺字段、同行审批、跨路径复用、替票与特殊豁免不由模型新增政策。真实目录、OA、付款、通知、财务工作簿和历史业务迁移不属于当前外部集成范围。模型识别不到不等同于允许跳过证据。
